# 要件ドキュメント

## 導入

本仕様は TLINY の既存データ管理機能を文書化します。対象は Firestore のデータモデリング、Repository/DataSource の契約、クエリとインデックス方針、一貫性/同時実行制御、エラーハンドリング、性能/コスト管理、セキュリティ整合、移行ポリシー、可観測性、テスト容易性です。目的は、MVVM + Repository と Firebase ベストプラクティスに整合しつつ、データ層を予測可能・テスト可能・スケーラブルにすることです。

## 要件

### 要件 1: データモデルとスキーマ

**目的:** 開発者として、明確に定義かつバージョン管理されたデータモデルが欲しい。これにより、安全にシリアライズ/デシリアライズでき、互換性を壊さずにスキーマを進化できる。

#### 受入基準（EARS）

1. WHEN エンティティモデルを定義する THEN データ層 SHALL 各エンティティの必須/任意フィールド、型、制約を文書化する。
2. IF フィールドが nullable または optional である THEN スキーマ文書 SHALL 既定値とフォールバックの規則を示す。
3. WHILE スキーマが進化する THE 文書 SHALL 破壊的/非破壊的変更ごとの履歴と移行注記を保持する。
4. WHERE Freezed モデルを使用する THE モデル SHALL 文書化されたスキーマを反映し JSON 変換のファクトリを提供する。

### 要件 2: Repository と DataSource の抽象

**目的:** 開発者として、安定した Repository インターフェースと下位 DataSource 契約が欲しい。これにより、Firebase 具体実装から Presentation/Domain を分離できる。

#### 受入基準（EARS）

1. WHEN UI からデータにアクセスする THEN Repository SHALL Firebase SDK 型をリークせず、Domain エンティティ（Future/Stream）を返す型付きメソッドを提供する。
2. IF Repository が複数 DataSource に依存する THEN Repository SHALL 呼び出しをオーケストレーションし、横断的一貫性ルールを隠蔽する。
3. WHERE 読み取り負荷の高い画面がある THE Repository SHALL 取得フィールドの選択とページネーションを提供する。
4. WHILE 継続更新が必要 THE Repository SHALL バックプレッシャー安全な Stream API を提供する。

### 要件 3: Firestore 操作とクエリ戦略

**目的:** システムとして、CRUD/クエリ/ページネーションの標準を定義し、効率とコスト予測性を確保したい。

#### 受入基準（EARS）

1. WHEN 複数ドキュメント書き込みを行う THEN システム SHALL 必要に応じてバッチ/トランザクションを用い原子的に実行する。
2. IF 複合並び替え/フィルタを要するクエリである THEN システム SHALL デプロイ前に複合インデックスを定義/供給する。
3. WHERE 大きな結果集合が想定される THE クエリ SHALL startAfter などのカーソルと明示的 limit を使用する。
4. WHILE ユーザーやイベントでスコープする THE クエリ SHALL 走査データを最小化するパス/コレクション設計を採用する。

### 要件 4: リアルタイムと一貫性

**目的:** 利用者として、必要に応じてリアルタイム更新を受け取りたい。これにより、過剰な読み取りなしに一覧/詳細が即時反映される。

#### 受入基準（EARS）

1. WHEN リアルタイムが業務上必須である THEN システム SHALL 重複状態の除去を伴う Stream リスナーを提供する。
2. IF 最終的整合で十分である THEN システム SHALL 要求時フェッチ（Future）を用い、ViewModel ライフサイクルでキャッシュする。
3. WHERE 競合更新が生じる THE システム SHALL 指定箇所でトランザクションまたはサーバタイムスタンプにより last-write-wins を維持する。
4. WHILE オフラインや不安定回線である THE システム SHALL Firestore クライアントキャッシュを活用し再接続時に整合させる。

### 要件 5: アクセス制御とセキュリティ整合

**目的:** セキュリティレビュー担当として、最小権限を保証するデータアクセスと Firestore/Storage ルールの整合を担保したい。

#### 受入基準（EARS）

1. WHEN Repository が読み書きを定義する THEN 対応する Firestore ルール SHALL 同一の述語とフィールド検証を強制する。
2. IF 書き込みにロール/所有権チェックが必要 THEN ルールと Repository 事前条件 SHALL 同一ロジックで文書化される。
3. WHERE サーバ専用操作が存在する THE システム SHALL Admin SDK を用いる Functions を経由し秘密情報をクライアントに露出しない。
4. WHILE 個人情報を扱う THE システム SHALL 権限主体に限定したフィールド公開と select 的取得で過剰取得を回避する。

### 要件 6: エラーハンドリングと可観測性

**目的:** 運用者として、行動可能でユーザーフレンドリーな失敗可視化と一貫したエラー変換が欲しい。

#### 受入基準（EARS）

1. WHEN Firebase 例外が発生する THEN DataSource 層 SHALL 安定コードの AppException カテゴリへマッピングする。
2. IF 操作が失敗する THEN Repository SHALL AppException を ViewModel に伝播し、安全な文言と診断情報を付す。
3. WHERE 繰り返し障害が発生する THE システム SHALL レート制御された記録と相関 ID を付してロギングする。
4. WHILE 本番運用中である THE システム SHALL データ操作に対しログ/監視（Crashlytics/Functions logs 等）を統合する。

### 要件 7: 性能とコスト管理

**目的:** コスト責任者として、SLA を満たしつつ Firestore コストを最小化するパターンが欲しい。

#### 受入基準（EARS）

1. WHEN コレクション一覧を取得する THEN システム SHALL 必要フィールドのみ取得し、limit と index を使って読取数を削減する。
2. IF 集計メトリクスを表示する THEN システム SHALL 適宜キャッシュ/事前計算または Functions を用いて算出する。
3. WHERE 高頻度更新がある THE システム SHALL バッチ書き込みと UI 発火のデバウンスで書込膨張を回避する。
4. WHILE 負荷が増大する THE システム SHALL 目標 p50 レイテンシを維持し、読取/書込を予算内に収める。

### 要件 8: データ移行とバックフィル

**目的:** 保守者として、スキーマおよび派生データの安全な移行により、既存利用者を壊さないようにしたい。

#### 受入基準（EARS）

1. WHEN 破壊的変更を導入する THEN システム SHALL バックフィルスクリプトや Functions ジョブを含む移行計画を提供する。
2. IF 移行期間中に二重読取/書込が必要 THEN Repository SHALL 旧新双方の読取と新形式での書込をサポートする。
3. WHERE 部分移行が可能 THE システム SHALL バージョンフィールドで移行済みを示し進捗を追跡する。
4. WHILE 移行を実行する THE システム SHALL ホットパーティションを避け、Firestore レート制限に従う。

### 要件 9: テストと検証

**目的:** QA として、データ挙動を一貫して検証できる自動テストとフィクスチャが欲しい。

#### 受入基準（EARS）

1. WHEN Repository を単体テストする THEN システム SHALL 成功/失敗経路を覆うフェイク/モックまたはエミュレータ連携テストを提供する。
2. IF 複合インデックスに依存するクエリである THEN 統合テスト SHALL エミュレータ設定済みインデックスで正当性を検証する。
3. WHERE 移行が発生する THE テスト SHALL 混在バージョンのデータセットで冪等性と正確性を検証する。
4. WHILE CI 実行中である THE データ層テスト SHALL Firestore エミュレータで実行し実コストを回避する。

### 要件 10: ドキュメントと図式

**目的:** チームメンバーとして、最新のドキュメントが欲しい。これにより、オンボーディングとレビューが効率化される。

#### 受入基準（EARS）

1. WHEN スキーマが変更される THEN 文書 SHALL フィールド表と JSON 例を更新する。
2. IF Repository 契約が変わる THEN 公開メソッドのシグネチャとデータフロー図 SHALL 更新される。
3. WHERE 新規インデックスが必要 THE `firestore.indexes.json` と根拠 SHALL 文書化される。
4. WHILE システムが進化する THE データドキュメント SHALL 設計/タスク各フェーズの単一ソースとして保たれる。
