# 実装ギャップ分析（data-management-documentation）

## 分析サマリ

- **機能スコープ**: 既存のデータ管理（Firestore モデリング、Repository/DataSource、インデックス/クエリ、整合性、セキュリティ、移行、可観測性、テスト）
- **主要ギャップ**:
  - Firestore ルールが全許可（allow read, write: if true）で、最小権限原則と不整合
  - 設計内のコレクション命名（例: items）が実装上の命名（products 等）と不一致
  - インデックス定義は一部（orders/events/products）のみ。設計で言及のインデックス（例: items: eventId+createdAt）未整備
  - ドキュメント化の深度（Repository 契約/クエリ一覧/エラーマッピング表/運用指標）が未反映
- **推奨アプローチ**: 既存パターンの拡張（Extension）を基本とし、命名整合とルール強化を最優先

---

## 既存コードベースの所見

- データモデル（Freezed）: `lib/src/data/model/`（product, order, user, ticket, program, favorite 等）。`exception/app_exception.dart` あり
- Repository 層: `lib/src/data/repository/` に各種実装（auth/product/order/...）。`BaseRepository` 抽象あり
- Functions: `functions/src/v2/*` にドメイン別実装（auth/business/firestore/payment/sns）。Admin 責務分離は概ね整合
- インデックス: `firestore.indexes.json` に `orders/events/products` 複合 index
- ルール: `firestore.rules` は全許可（開発用）で本番要件と乖離

---

## 要件実現に向けたギャップ一覧

1. セキュリティ整合（最小権限）

- 現状: 全許可
- 必要: 画面/Repository 事前条件に対応したルール（所有者/ロール/イベントスコープ/フィールド検証）
- 影響: 全 API に横断。優先度: 最高

2. 命名・スキーマ整合

- 現状: 実装は `products` 等、設計では `items` を使用
- 必要: 設計ドキュメントの命名を実装に合わせて修正、または移行方針（items へ統一）を決定
- 影響: 設計/タスク/将来の移行計画。優先度: 高

3. インデックス網羅

- 現状: `orders/events/products` のみ一部定義
- 必要: 画面クエリ要件に基づく追加定義（例: `products: eventId+createdAt` 等）。`requirements.md` のクエリ戦略に対応
- 影響: 検索/一覧/ダッシュボードの性能とコスト。優先度: 中〜高

4. Repository 契約のドキュメント化

- 現状: コードは存在するが、公開メソッドの入出力/前後条件/不変条件の表が未作成
- 必要: 設計/タスクに沿った契約表の作成とリンク
- 影響: テスト容易性・保守性。優先度: 中

5. エラーハンドリングの整合表

- 現状: `AppException` あり。FirebaseException のマッピング表は未ドキュメント
- 必要: 例外コード/カテゴリ/ユーザー提示方針/再試行方針を表化
- 影響: 運用・UX。優先度: 中

6. 性能/コスト指標の明文化

- 現状: 一般指針はあるが、指標値（目標 p50、上限 R/W/費用）と測定法が未定義
- 必要: 具体指標の設定と監視ポイント定義
- 影響: 運用コスト。優先度: 中

7. 移行/バックフィル手順

- 現状: 設計に方針あり。具体手順・ロールバック条件は未ドキュメント
- 必要: 段階移行手順書（エミュレータ/本番）、レート制限・ホットパーティション回避
- 影響: リリース安全性。優先度: 中

---

## 実装戦略オプション

- アプローチ A（Extension: 既存拡張）

  - 根拠: 既存の Repository/モデル/Functions が充実
  - トレードオフ: 命名不一致はドキュメント修正で対処（移行は後続）
  - 複雑度: M（3-7 日）

- アプローチ B（Hybrid: 一部新設）
  - 根拠: セキュリティ/監視/契約表などドキュメントと設定を新設
  - トレードオフ: 新規作成分の教育/レビューコスト
  - 複雑度: M

---

## 技術リサーチが必要な領域

- Firestore ルール設計のベストプラクティス（イベント/ユーザー/ロールベース）
- FlutterFire でのフィールド選択的取得（select 相当）の可否と代替（軽量 DTO 化・コレクション分割）
- 高頻度更新時の最適化（クライアントキャッシュ/デバウンス/トランザクション設計）

---

## 推奨事項（設計/実装に向けて）

1. ルール強化を最優先で対応（最小権限、所有者/ロールチェック、書込フィールド検証）
2. 設計内の命名を実装に整合（`items`→`products` へ修正）し、必要なら移行計画を別途策定
3. 画面要件ベースでインデックス追補し、`firestore.indexes.json` を更新
4. Repository 契約表・例外マッピング表・運用指標（SLO/コスト）を `docs/` または spec 配下に追加
5. テスト: インデックス前提クエリ/移行冪等性/Repository 例外マッピングをエミュレータで自動化
